Что можно построить, когда каждый пиксель окна — наш: C++23, Direct2D, DirectWrite, DirectComposition, Direct3D 11, DXGI, DWM, Win32. Исследование 05.11.2026. Исходный код и действующий дизайн не менялись: это карта возможностей, а не план переделки.

Исходные факты

  • Сейчас.
    • Окно рисует ID2D1HwndRenderTarget; фабрика D2D — main_window.cpp:967.
    • Текст — DirectWrite с Geist из памяти, ClearType.
    • SVG-значки — через ID2D1DeviceContext5, полученный у той же цели (icons.cpp).
    • Своя шапка — через WM_NCCALCSIZE.
    • Кадры — по vsync в EndDraw.
    • Частицы — на CPU через FillEllipse: до 600 штук, у каждой 3 «призрака» и ореол. Они уже от данных: три потока (VPN, WARP, напрямую), частота и размер растут с байтами в секунду. Кружат вокруг кубика-переключателя (cube.h).
    • Снимки — программная WIC-цель, около main_window.cpp:6874.
    • В линковке нет d3d11, dxgi, dcomp.
  • Анимации Windows у него выключены. Motion() читает SPI_GETCLIENTAREAANIMATION и возвращает false. Значит, идеи без неподвижной формы для него не существуют. Это стало критерием: в «Целесообразности» у каждой идеи сказано, как она выглядит без движения.
  • Видеокарта — GTX 750 Ti. Direct3D feature level 11_0, вычислительные шейдеры cs_5_0 есть. HDR-вывода почти наверняка нет (HDMI 1.4), так что HDR-идеи у него не проверить.
  • PangoBright затемняет экран ×0,557. Цвета на снимках поэтому не истина. А ступеньки в тёмных переходах у него видны сильнее, чем у других.
  • Версии. Windows 10 LTSC 2021 — это сборка 19044.
    • Только Windows 11: всё, что в SDK 10.0.26100 спрятано под NTDDI_WIN10_CO, …_CU или …_NI. Например, ID2D1DeviceContext7, IDWritePaintReader, статистика композитора DComp.
    • Есть и в LTSC 2021 всё нужное основным идеям: ID2D1DeviceContext3 (1511), ID2D1DeviceContext6 (1709), IDWriteTextLayout4 и IDWriteFactory6 (1709), D2D-эффекты HDR (1809). Проверено по заголовкам.
  • Закон (docs/design/law.md) — фильтр целесообразности.
    • Цвет = судьба потока: VPN 76,146,255, WARP 232,134,66, напрямую 160,165,176, блок 240,96,96.
    • Рука пользователя — белая. Вердикты — зелёный и янтарный.
    • Судьба — линия, а не плоскость: рельс 3 DIP, кромка 1 DIP. Прозрачность не несёт смысла.
    • Круг — состояние, прямоугольник — вещь.
    • Geist только 400 и 600.
    • Движение только показывает поток или изменение: 90, 160 или 240 мс.
    • Нет градиентов, теней, стекла и свечения без состояния.
    • Контраст текста ≥4,5, графики ≥3,0, ΔE между судьбами ≥30.

Слой 0 — что сделать один раз

Большинство идей упирается не в эффект, а в то, на чём рисуем. Ступеней три, и каждая не ломает предыдущую.

0a — тот же HWND, другой интерфейс

У существующей цели запрашиваем ID2D1DeviceContext через QueryInterface: icons.cpp уже так получает ID2D1DeviceContext5. Окно, ClearType, шапка и дочерний EDIT не меняются. Что открывается:

  • Встроенные эффекты D2D: размытие, морфология, цветовые матрицы, композиция, освещение (PointSpecular, SpotDiffuse…), турбулентность, перспектива.
  • Свои эффекты на HLSL: ID2D1Factory1::RegisterEffectFromString плюс ID2D1EffectImpl/ID2D1DrawTransform. Шейдеры — DXBC от fxc (ps_4_0/ps_5_0): D2D стоит на D3D11, DXIL от dxc он не возьмёт.
  • ID2D1SpriteBatch (DC3, Windows 10 1511): тысячи спрайтов одним вызовом.
  • BlendImage (DC6, 1709): режимы наложения.
  • SetPrimitiveBlend(D2D1_PRIMITIVE_BLEND_ADD): сложение света.
  • Битмапы FP16 вне экрана: D2D1_BITMAP_OPTIONS_TARGET + DXGI_FORMAT_R16G16B16A16_FLOAT. Поддержку проверяет IsBufferPrecisionSupported(D2D1_BUFFER_PRECISION_16BPC_FLOAT).
  • ID2D1CommandList: записанный кадр, который можно перерисовать в другом масштабе.

Чего 0a не даёт: HDR и 10-битного вывода, прозрачного окна, слоёв композитора.

0b — своя цепочка обмена

Как устроено:

  • D3D11CreateDevice с D3D11_CREATE_DEVICE_BGRA_SUPPORT, откат — WARP.
  • Swap chain в flip-модели: CreateSwapChainForHwnd, DXGI_SWAP_EFFECT_FLIP_DISCARD.
  • ID2D1Device → ID2D1DeviceContext на заднем буфере.
  • В линковку добавить d3d11 dxgi.

Что даёт:

  • FP16/scRGB при включённом расширенном цвете;
  • ожидание кадра (FRAME_LATENCY_WAITABLE_OBJECT);
  • Present1 с грязными прямоугольниками;
  • общее D3D11-устройство для вычислительных шейдеров.

Главный риск — дочерний EDIT (main_window.cpp:6245). С WS_EX_NOREDIRECTIONBITMAP у окна нет поверхности перенаправления, и GDI-ребёнка не видно. А flip-цепочка поверх окна с GDI-детьми официально не гарантирует, что ребёнок останется сверху. Три выхода, по возрастанию цены:

  1. CreateSwapChainForHwnd без NOREDIRECTIONBITMAP — и проверить на месте, что EDIT виден и не мерцает. Начинать с этого.
  2. EDIT в собственном безрамочном всплывающем окне-владельце над полем ввода; оно двигается вместе с окном.
  3. Свой ввод текста — дороже всего: IME через TSF, выделение, буфер обмена, UI Automation.

0c — окна-спутники на DirectComposition

Всё новое верхнеуровневое — шар, линия по краю экрана, наложения, прицел, оторванные чипы — сразу делается на DComp:

  • WS_EX_NOREDIRECTIONBITMAP;
  • общее D3D11-устройство → DCompositionCreateDevice → CreateTargetForHwnd;
  • поверхность IDCompositionSurface с premultiplied alpha, D2D рисует внутри BeginDraw.

Получаем прозрачность по пикселю без UpdateLayeredWindow, а анимации крутит композитор, а не наш поток. Главное окно эта ступень не трогает. Общий модуль — src/tray/gfx/dcomp_window.{h,cpp}; в линковку добавить d3d11 dxgi dcomp.

Правила для всех ступеней

  • Главное окно остаётся непрозрачным. ClearType живёт только на непрозрачной цели; на цели с premultiplied alpha D2D переходит на серое сглаживание. В спутниках текст будет серым — для коротких надписей это допустимо.
  • Плавные слои считаются в FP16 отдельно — ореолы, свет, выдержка. Текст и кромки рисуются прямо в цель, чтобы ClearType не страдал.
  • Снимки. Проверить, считает ли программная WIC-цель (main_window.cpp:6874) наши эффекты. Если нет — путь D3D11 WARP → ID2D1DeviceContext → битмап → WIC. Это же основа эталонных снимков для тестов (B12).
  • Модальный диалог. Пока он открыт (Blocked()), наши кадры стоят; анимации композитора DComp при этом идут.
  • Новые интерфейсы. Всё, что под NTDDI_WIN10_CO и новее, подключать по факту наличия (QueryInterface/GetProcAddress), а не по номеру версии ОС.

A — практически недоступно для Web UI

Уровень рендеринга: яркость сверх белого, общая световая сцена, маски из глифов, режим хинтинга по кадрам, контуры глифов из системного шейпера, знание о движении окна. В браузере это либо закрыто, либо доступно, только если отказаться от DOM и перенести весь интерфейс в один холст.

HDR-лампы: состояние светит ярче бумаги

LTSC 2021 ✓Windows 11 ✓слой 0bсложность 4/5потом

Что
На мониторе с включённым HDR лампы и рельсы судьбы выводятся ярче белого текста — в 1,3–1,6 раза от уровня SDR-белого. Всё остальное остаётся ровно в SDR-белом. Свет перестаёт быть нарисованным ореолом и становится светом. На обычном мониторе ничего не меняется.
Как выглядит
Текст, кромки и карточки — «бумага» той же яркости, что у всех окон. Ядро лампы VPN заметно ярче самого белого на экране. Глаз читает его как источник, а не как краску, и находит периферийным зрением. Ореол .12 можно сделать тоньше: светит само ядро.
Как работает
  • Swap chain R16G16B16A16_FLOAT + SetColorSpace1(DXGI_COLOR_SPACE_RGB_FULL_G10_NONE_P709): scRGB, линейный, 1,0 = 80 нит.
  • Интерфейс рисуется в SDR и проходит эффект WhiteLevelAdjustment — до SDR-белого пользователя. Уровень берётся из DisplayConfigGetDeviceInfo с DISPLAYCONFIG_DEVICE_INFO_GET_SDR_WHITE_LEVEL.
  • Лампы получают множитель сверх этого уровня.
  • В конце — HdrToneMap к максимуму экрана из IDXGIOutput6::GetDesc1.
  • Включён ли HDR, видно по DXGI_OUTPUT_DESC1::ColorSpace (…G2084…P2020). Перепроверять при WM_DISPLAYCHANGE и при переезде окна на другой монитор.
Технологии
DXGI 1.6, D2D 1.1 на FP16, эффекты CLSID_D2D1WhiteLevelAdjustment и CLSID_D2D1HdrToneMap (d2d1effects_2.h, под NTDDI_WIN10_RS5), DisplayConfig.
Сложность
4/5. Сам вывод — пара дней. Трудно другое: переключение SDR↔HDR на лету (окно между двумя мониторами; HDR включили при открытом окне) и поведение ClearType на FP16-цели — вероятно, станет серым, надо проверить.
Отличие от Web
Элементу DOM нельзя задать яркость выше белого. В Chromium это есть только у HDR-картинок и видео и у WebGPU-холста с toneMapping: "extended". Пришлось бы весь интерфейс перенести в холст.
Ценность
Иерархия по физической яркости, а не по насыщенности: цвет остаётся только для смысла. Но увидят это лишь владельцы HDR-мониторов, а их немного.
Реализуемость
Эффекты есть с 1809, то есть в LTSC 2021 и в 11. Windows 11 24H2 даёт ещё …GET_ADVANCED_COLOR_INFO_2. Нужна ступень 0b с её риском для EDIT. У него HDR-вывода нет: проверять на другой машине или по FP16-снимкам через WARP.
Целесообразность
Закон («свечение только у состояния») соблюдён: ярче только лампы. Риск — слепящее ядро на тёмном фоне, поэтому потолок 1,6× и только у ламп и рельс, не у текста. Неподвижная форма у идеи и так есть. Вердикт: потом. Но FP16-путь из A2/B9 строить так, чтобы HDR включался одним флагом.
Путь
  1. После 0b выбирать формат цепочки по GetDesc1().ColorSpace.
  2. Сцену считать в FP16 линейно. SDR-часть пропускать через WhiteLevelAdjustment; лампам — множитель kLampHdrGain в ui_style.h.
  3. HdrToneMap: на входе наш максимум, на выходе MaxLuminance монитора.
  4. На WM_DISPLAYCHANGE и WM_WINDOWPOSCHANGED + MonitorFromWindow — пересоздать цепочку.
  5. Проверка без HDR-монитора: WARP + FP16 → JPEG XR через WIC (GUID_ContainerFormatWmp хранит float); сверить значения ламп.

Единая модель света в линейном FP16

LTSC 2021 ✓Windows 11 ✓слой 0aсложность 3/5попробовать

Что
Вместо отдельного ореола у каждой лампы — одна световая карта сцены. Излучатели (лампы, рельсы, частицы) пишут свет в линейный FP16-буфер. Приёмники берут из него освещённость: кромки 1 DIP, края карточек, ободки. Свет не красит плоскости — он ложится только на кромки рядом с источником.
Как выглядит
Ничего не светится «просто так». Кромка карточки рядом с синим рельсом чуть подсвечена синим с ближней стороны, дальняя сторона нейтральна. Поток ушёл на WARP — отсвет на соседних кромках стал оранжевым. Интерфейс сам показывает, какие элементы под каким маршрутом. Вклад частиц усредняется во времени, поэтому кромки не мерцают.
Как работает
  1. Излучатели. Лампы, рельсы и частицы рисуются в FP16-битмап с разрешением в 1/4 и ADD.
  2. Поле. Каскад уменьшений и размытие дают поле освещённости.
  3. Маска приёмников. Те же DrawRoundedRectangle кромок рисуются в A8-битмап, кеш до смены раскладки.
  4. Сборка. Свет умножается на маску (ArithmeticComposite) и ложится на кадр через BlendImage(LINEAR_DODGE).
  5. Блик (по желанию). Альфа кромки, размытая на 1 DIP, служит картой высот для PointSpecular с источником в координатах лампы. Получается блик на ближней грани, как в тиснении.
Технологии
ID2D1DeviceContext (0a), FP16-битмапы, GaussianBlur, ArithmeticComposite, BlendImage, PointSpecular. Позже — свой HLSL-эффект «свет × маска» одним проходом.
Сложность
3/5. Техника известная — отложенное освещение в 2D. Трудна калибровка: чтобы свет не превратился в неоновую вывеску.
Отличие от Web
В CSS нет поля освещённости, которое знает о соседних элементах. box-shadow у каждого элемента — это нарисованный ореол: он не складывается между источниками и не маскируется приёмниками. В WebGL можно всё, но тогда весь интерфейс уходит в холст, а текст теряет системный рендер и доступность.
Ценность
Судьба потока видна не только на рельсе, но и на всём, что рядом: сцена связная. Свет становится носителем смысла.
Реализуемость
Хватает 0a, окно не меняется. BlendImage — с 1709, иначе Composite (Windows 8+). GTX 750 Ti в 1/4 разрешения справится с запасом. Работают ли эффекты на WIC-цели снимков — проверить.
Целесообразность
На грани закона. «Свечение только у состояния» соблюдено. «Свет не красит плоскость» держится на маске приёмников. Опасность — эстетика игрового RGB. Без анимаций свет статичен: его дают лампы и рельсы, а частицы — через выдержку B2. Вердикт: попробовать в макете и оставить, только если отсвет на кромке читается как информация.
Путь
  1. src/tray/gfx/light_field.{h,cpp}: LightField::Resize(size, dpi), BeginEmit(), EmitLamp(pt, color, power), EmitRail(geometry, color), EndEmit(), Apply(dc, receivers).
  2. В Paint излучатели брать из тех же данных, что рисуют лампы (цвета судеб — ui_style.h).
  3. Маску приёмников строить при смене раскладки.
  4. Коэффициенты kLightGain и kLightRadius держать в ui_style.h, чтобы их правил дизайн, а не код.

Страж контраста: фон гаснет под текстом

LTSC 2021 ✓Windows 11 ✓слой 0aсложность 2/5делать

Что
Частицы, отсветы и любые живые слои не опускают контраст текста ниже 4,5. Под каждым глифом лежит маска — контур текста, расширенный морфологией, — и в ней фоновая графика приглушается. Это рантайм-гарантия ворот контраста из закона, а не надежда, что частица не пройдёт под цифрой.
Как выглядит
Частица под словом не исчезает рывком. Она уходит в узкий «зазор» вокруг букв: в 2 DIP от контура глифа её яркость плавно гаснет. Текст читается одинаково и на пустом фоне, и на плотном потоке. Так картографы выбивают фон вокруг подписей на карте.
Как работает
  1. Текст рисуется в A8-маску (кеш по раскладке).
  2. Morphology (DILATE, ~2 DIP) и GaussianBlur на 1 DIP дают мягкий ореол-маску.
  3. Живые слои рисуются отдельно, маска вычитается из них: Composite с DESTINATION_OUT.
  4. Точная версия — свой эффект. Он считает яркость фона под маской и ограничивает её так, чтобы контраст к цвету текста по формуле WCAG не упал ниже 4,5.
Технологии
Эффекты D2D Morphology, GaussianBlur, Composite (0a); свой эффект — для точного порога.
Сложность
2/5 для маски, 3/5 для точного порога в шейдере.
Отличие от Web
В CSS нет маски «из глифов соседнего слоя». text-shadow и -webkit-text-stroke рисуют поверх, а не вырезают фон. mask-image берёт картинку, а не текст элемента. В холсте можно, но тогда весь текст рисует само приложение.
Ценность

Глифы как геометрия

Что
Буквы становятся контурами, с которыми можно делать всё, что с геометрией. Три применения:

  • заблокированный домен показан пустотелым — только контур, без заливки;
  • при блокировке имя разбирается на точки по контуру и уходит в поток.
Как выглядит
  • Вдоль пологого участка синего рельса мелко написано «telegram.exe · 3 соединения». Каждая буква повёрнута по касательной.
  • Заблокированное имя — красный контур 1 DIP без заливки: «пустое слово» читается как «не пускают». Это и неподвижная форма.
  • С анимациями: в момент блокировки имя рассыпается на ~200 точек и застывает пустым контуром.
Как работает
  • Контуры. Свой IDWriteTextRenderer для готового layout. В DrawGlyphRun вызывается IDWriteFontFace::GetGlyphRunOutline в ID2D1PathGeometry. Кернинг и лигатуры сохраняются, потому что позиции уже сформованы.
  • Текст по кривой. ID2D1Geometry::ComputePointAtLength даёт точку и касательную для центра каждого глифа, глиф ставится трансформом.
  • Точки. ComputeLength + равномерная выборка по длине контура.
  • Кеш. ID2D1GeometryRealization.
Технологии
DirectWrite (свой text renderer, GetGlyphRunOutline), геометрия D2D, CreateStrokedGeometryRealization (DC1, 8.1+).
Сложность
2/5 для пустотелых имён. 3/5 для текста по кривой: на изгибах буквы налезают с внутренней стороны.
Отличие от Web

Ценность
Имя и маршрут связаны физически: имя лежит на своей линии, легенда не нужна. Блок получает форму, а не только цвет. Пустотелое имя — компактный и однозначный знак.
Реализуемость
Все версии. У контура нет хинтинга: на 12,5 DIP контурный текст мутнее ClearType. Поэтому контуры — для пустотелых имён и текста ≥14 DIP, обычный текст остаётся DrawTextLayout.
Целесообразность
«Судьба — линия»: текст на рельсе закону подходит. Пустотелое имя — новый знак, который дизайнеру надо принять. Рассыпание — движение, показывающее изменение; без анимаций сразу пустотелое имя. Вердикт: попробовать пустотелые имена (дёшево и сильно); текст по рельсу — в макете.

  • TextOnPath(path, layout, offset) возвращает набор «геометрия + трансформ».

Частицы от реальных соединений: дорожки программ

Что
Развитие того, что уже есть. Сейчас LiveTraffic рождает точки по байтам в секунду трёх потоков: VPN, WARP, напрямую. Следующий шаг:

  • скорость точки обратно пропорциональна задержке маршрута (RTT);
  • частота, как сейчас, — от байтов в секунду.
Рисование переходит с поштучного FillEllipse на спрайтовый пакет: тысячи точек за один вызов.

  • Данные. Ядро (sing-box API соединений) уже знает процесс у соединения, если включён find_process: для блока это сделано в 0.5.107. Нужен агрегат «программа → байты/с, RTT маршрута».

  • Рисование. ID2D1SpriteBatch::AddSprites: прямоугольник, исходник в атласе, цвет, трансформ. DrawSpriteBatch требует D2D1_ANTIALIAS_MODE_ALIASED на время вызова.
  • Сложение. Ореолы складываются через SetPrimitiveBlend(ADD).
  • Порядок формул DotsPerSecond / DotSize / DotSpeed сохраняется, к скорости добавляется множитель от RTT.
Технологии
ID2D1DeviceContext3 (SpriteBatch, 1511+), атлас ID2D1Bitmap1, SetPrimitiveBlend, API ядра.
Сложность
3/5. Рисование — 2/5. Агрегат по программам в ядре и раскладка дорожек, чтобы они не путались, — основная работа.
Отличие от Web
Canvas 2D на тысячах точек упирается в CPU, WebGL — нет; это Web может. Не может он другое: знать, какой программе принадлежит соединение. Это знание ядра и ОС, а не графики. Нативно данные и рисунок живут в одном процессе без моста.
Ценность
Поток становится картой: кто сколько тянет и по какому маршруту — без таблицы. Это главная «живая» идея, а B2 даёт ей неподвижную форму.

Целесообразность

Длинная выдержка: поток как фотография

LTSC 2021 ✓Windows 11 ✓слой 0aсложность 2–3/5делать первым из живого

Что
Поток показывается так, как его сняла бы камера с выдержкой в несколько секунд: следы точек сливаются в светящиеся траектории. Яркость траектории — сколько данных по ней прошло за последние ~3 с. Это неподвижная форма для всего живого (B1, B3, D6, D7) и потому — главный режим для пользователя с выключенными анимациями.
Как выглядит
  • Вокруг кубика — тонкие непрерывные линии судеб разной яркости: «нити света», как на ночном снимке шоссе.
  • Толстая яркая синяя нить — основная нагрузка через VPN. Бледная оранжевая — немного через WARP. Красные обрывки у грани — блоки.
  • Без анимаций картинка обновляется раз в 1–2 с, без переходов. Это не мерцание, а смена фотографии.
Как работает
Два варианта.
  • Аналитический (дешевле, работает и на WIC-цели). Траектория дорожки — геометрия; ширина и яркость — от интеграла пропускной способности за τ. Рисуется DrawGeometry один раз в цикл.
  • Накопительный. FP16-битмап, каждый кадр: acc = acc·e−Δt/τ + новые точки. Затухание — ColorMatrix, точки — с ADD. Затем тональная кривая в SDR, чтобы плотные места не выгорали в белое.
Технологии
FP16-битмапы, ColorMatrix, SetPrimitiveBlend(ADD), тональная кривая (TableTransfer или свой эффект). Для аналитики — только геометрия D2D.
Сложность
2/5 аналитический, 3/5 накопительный (калибровка τ и кривой).
Отличие от Web
В WebGL накопитель делается, в Canvas 2D — только 8 бит, с полосами при затухании. Главное отличие не в возможности, а в том, что у нас это тот же кадр, что и остальной интерфейс, с тем же текстом и ClearType.
Ценность
Отвечает на вопрос «куда шёл трафик последние секунды» одним взглядом, без графика. И делает живую часть интерфейса видимой ему.
Реализуемость
0a, все версии. Накопитель — 1–2 МБ видеопамяти.
Целесообразность
Полностью в законе: «судьба — линия», движение показывает поток, и есть неподвижная форма. Это не декор: яркость — данные. Вердикт: делать первым из «живого».
Путь
  1. src/tray/gfx/exposure.{h,cpp}: Exposure::Add(lanePath, color, bytes), Exposure::Draw(dc, now).

В Web это делается (FLIP-анимации, transition-delay). Естественнее у нас потому, что один кадр и одна модель: волна выходит за окно — в трей и рамку, а странице это недоступно.

Везде, без новых API.

Реализуемость

Целесообразность

Гильош ключа: отпечаток сервера как защитная сетка

Что

Слева — ключ A, справа — ключ A′, отличающийся одним битом. В эскизе — простой хеш JS; в клиенте — SHA-256.

Как работает

  3. Геометрия — ID2D1PathGeometry по ~2000 точкам; кеш в ID2D1GeometryRealization (рисуется дёшево каждый кадр).
Технологии
BCrypt, геометрия D2D, CreateStrokedGeometryRealization.
Сложность
2/5 рисунок. 3/5 — подбор пространства параметров, чтобы близкие хеши давали далёкие картинки и любая картинка была красивой.
Отличие от Web
Технически в SVG/Canvas можно. Отличие в качестве: тонкие линии 0,5 DIP с аналитическим сглаживанием D2D против пересэмплирования Canvas, и кеш реализаций. И ключ сервера в процессе, а не в JS.
Ценность
Безопасность, ставшая образом: подмена сервера заметна. И знак, который больше никто не делает — основа своего языка.
Реализуемость
Везде. Тонкие линии на 100% масштабе сливаются — минимум 0,75 DIP при 96 dpi.
Целесообразность
Линия, без заливки, без цвета — в законе. Без анимаций — то же. Вердикт: делать, это ядро языка.

10 самых перспективных

Критерий: польза × соответствие закону × видно ли ему (анимации выключены) ÷ цена. У каждой — первый шаг, который можно сделать отдельно.

  1. C1 Судьба под курсором — снимает главный барьер маршрутизации по программам. Первый шаг: прицел → путь exe → готовое правило, без рамки-наложения.
  2. B2 Длинная выдержка — делает поток видимым ему и превращает частицы в данные. Первый шаг: аналитический вариант по трём существующим потокам, только при !Motion().
  3. B4 Честные цифры — исполнение закона и закрытие пункта 5 аудита. Первый шаг: tnum на всех меняющихся числах.
  4. C4 Значок-прибор — состояние без открытия окна. Первый шаг: лампа судьбы в значке, без полоски скорости.
  5. D1 Гильош ключа — безопасность как образ, ядро языка. Первый шаг: розетка в карточке сервера из public_key Reality; подобрать параметры на 50 ключах.
  6. B3 Изменение от причины — побочные эффекты правил становятся видимыми. Первый шаг: волна на каталогах «Блока» (случай «Microsoft → GitHub»).
  7. C2 Рентген маршрутов — «что идёт мимо VPN» за секунду. Первый шаг: один монитор, снимок на нажатие, без слежения за движением.
  8. D4 Кубик-призма — соотношение маршрутов без диаграммы. Первый шаг: неподвижный кадр в HTML-макете, затем в cube.h.
  9. C3 Линия по краю экрана — честность автоматических решений. Первый шаг: только на событие «kill switch сработал».
  10. C11 Секреты вне снимков — прямая защита от утечки подписки. Первый шаг: отдельное окно с QR и ссылкой.

  1. C5 Рамка окна — 1/5. Один вызов DWM, а окно говорит состояние формой.
  2. B4 Честные цифры — 1–2/5. Цифры перестают дрожать, точность видна.
  3. C4 Значок-прибор — 2/5. Состояние всегда на виду.
  4. D4 Кубик-призма — 2/5. Самый сильный образ из дешёвых.
  5. D7 Огибающая дрожания — 1/5. Новый знак в строке сервера за вечер.

Следующие — B3 и пустотелые имена из A5.

Единая графическая система: «Линия судьбы»

Общий корень идей, прошедших отбор: данные нарисованы линией. Так в приборах, гравюре и защитной печати. Это продолжает закон («судьба — линия, а не плоскость») и отличает Sovereign от «плоских» и «стеклянных» интерфейсов. Четыре слоя.

  1. Свет и поток.
    • B1 дорожки программ + B10 размытие движения + B2 выдержка + D6 фосфор;
    • A3 страж контраста и B9 дизеринг как гарантии;
    • A2 — если пройдёт макет; A1 — потом.
    Общее: один FP16-накопитель, один атлас спрайтов, модуль src/tray/gfx/flow/. Неподвижная форма всего слоя — выдержка.
  2. Защитная печать.
    • D1 гильош, D3 штриховка, D2 микротекст с B11 лупой;
    • A5 пустотелые имена, B5 анатомия домена;
    • C11/C12 — секреты и печать Hello;
    • (+D11 для резкости линий).
    Общее: тонкие нейтральные линии для идентичности и доверия; цвет остаётся только у судеб.
  3. Судьба по всей Windows.
    • C1 прицел, C2 рентген, C3 край экрана;
    • C4 значок, C5 рамка, C9 панель задач, C10 палитра.
    Волна B3 доходит до значка и рамки, то есть изменение видно и вне окна. Общее: dcomp_window, поиск процесса по окну, источник событий «Клиент решил сам».
  4. Общая основа. Слой 0 (0a → 0c → 0b), B12 часы и эталонные снимки, C13 бюджет графики. Правило системы: у каждой идеи есть неподвижная форма, и она проверяется снимком.

Порядок работ

  1. Без инфраструктуры: B4, C5, D7, B3, пустотелые имена A5, D4 в макете.
  2. Ступень 0a: B2, A3, B9, D1, B1+B10. Сюда же часы и WARP-снимки B12.
  3. Ступень 0c: C3, C1, C2, рост окна C4, C6.
  4. Система вокруг: C9, C10, C11/C12, C13.
  5. Ступень 0b (после решения про EDIT): A1, B7, 10 бит.
  6. Эксперименты: D2+B11, D3, D11, A2.

Windows 10 LTSC 2021 и Windows 11

  • Всё, кроме трёх пунктов, работает на обеих: нужные интерфейсы — 1511, 1709 и 1809, а WDA_EXCLUDEFROMCAPTURE — с 2004. LTSC 2021 — 21H2 (19044).
  • C5 — на Windows 10 атрибут игнорируется: окно остаётся с обычной рамкой, без ошибки.
  • C13 — режим Energy Saver есть только в Windows 11; на 10 — обычная «экономия батареи».
  • A1 — расширенная информация о цвете (…ADVANCED_COLOR_INFO_2) только в 11 24H2; на 10 — старый путь, тоже рабочий.
  • C12 — минимальная версия interop-метода не проверена; запасной путь — CredUI.

Реализуемость против целесообразности

  • Просто и ясно — делать первыми: C5, B4, D7, D4, C11, C4.
  • Трудно, но ясно — стоят своей цены: C2, A1, B7, B12, B1.
  • Просто, но спорно — решает дизайн, не код: A2, A6, D9, D10, D2, вес 385 из A4.
  • Трудно и спорно — только как эксперимент: D11, SDF-шов из B6.
