# Self-hosted: свой сервер в клиенте (набросок, 06.11.2026)

Не код, а карта: куда что кладётся и как уживается с подписками. Решения 06.10 из памяти
(касты отменены 16.10, остаётся «карточка своего сервера» в общем списке) и то, что уже есть в коде.

## Что уже есть и на что опираемся

- `Profile` (profiles.h): одна запись = подписка (`url`) или свой конфиг (`url` пуст). Все включённые
  (`enabled`) работают вместе, `CombineConfigs` (combine.h) собирает один конфиг: рамка (inbounds, DNS,
  routing) от первого, серверы от всех, у каждого тег `<тег> · <имя профиля>`.
- `Profile::via` — цепочка: серверы профиля ходят через другой профиль (двойной хоп).
- `Profile::paidTill`, `supportUrl` — уже есть «до какого числа оплачен свой сервер» (support_report.h).
- Личная папка `profiles\<id>\` с `config.json` — туда же ляжет конфиг, который сгенерирует клиент.

Вывод: **свой сервер — это ещё один Profile**, а не новый механизм. Совмещение с подпиской уже
работает (оба `enabled`, серверы в одном списке, `auto` выбирает лучший по замеру).

## Модель данных

К `Profile` добавить необязательный блок `own` (его нет — обычный профиль):

| поле | что |
|---|---|
| `host`, `sshPort`, `sshUser` | куда ставили |
| `keyRef` | имя секрета в хранилище клиента (не сам ключ, не пароль в tray.json) |
| `installed` | какие протоколы поставлены (reality / hysteria2 / naive …) и версия скрипта |
| `shared[]` | пользователи «Поделиться»: id, имя, лимит, срок, выключен ли (позже) |

`url` у такого профиля пуст — обновление по расписанию не нужно, конфиг пересобирается самим клиентом
при изменении `own`. `userinfo/traffic` берём с сервера по SSH (позже).

## Карточка в списке

Тот же список «Конфиги», другой вид карточки: имя, адрес, статус («работает / не отвечает»), «Оплачен до»,
кнопки: **Отчёт**, **Поделиться**, **Переустановить**, **Удалить с сервера**.
Первый экран при пустом списке получает третью кнопку «Поставить свой сервер» рядом с «Добавить подписку».

## Установка (по SSH, как Amnezia)

1. Форма: адрес, пользователь, пароль или ключ (пароль только на время установки, потом — ключ клиента,
   секрет в хранилище).
2. Клиент по SSH проверяет ОС, порты, что уже стоит; показывает план (что поставит, какие порты откроет).
3. Ставит: тот же скрипт, что packetlab (его логика уезжает в клиент), с прогрессом по шагам
   (как теперь у обновления: «Шаг 3 из 7 · …»).
4. Результат: ссылки/конфиг → новый Profile с `own`, включён сразу.
5. Лог установки сохраняется в `profiles\<id>\install.log` — это и есть основа отчёта для нейронки.

## Как совмещается с подпиской

- **Рядом**: оба включены, один список серверов. Режим «авто» сам выбирает; можно закрепить свой.
- **Свой как выход, подписка как вход** (`via`): подписка → свой сервер: сайт видит адрес своего сервера,
  провайдер подписки видит только трафик до него. Это уже умеет `via`; в карточке — одна строка
  «Выход через: …».
- **Правила по маршрутам**: в «доске маршрутов» путь «через VPN» сегодня один. Нужен выбор
  «через какой профиль» для корзины/сервиса (например, Netflix — через свой сервер). Минимум — тег-фильтр
  по профилю в правиле; это изменение routing.cpp, отдельный шаг.
- **Kill switch / обновления**: не затрагиваются, адрес своего сервера уже в конфиге как сервер, исключения делаются по нему.
  (SubscriptionHosts не трогать: он гонит хосты подписок ЧЕРЕЗ VPN, для своего сервера это петля.)

## Порядок работ (каждый шаг выпускается отдельно)

1. Данные: `own` в Profile + (де)сериализация + тесты; профиль «свой сервер» добавляется вручную из
   готовой ссылки (без установки) — сразу видно, как он живёт рядом с подпиской. Карточка с его видом.
2. SSH-слой: встроенный клиент (libssh2 или системный `ssh.exe`?), запуск скрипта, чтение вывода, прогресс.
3. Установщик: скрипт packetlab как ресурс, шаги, откат при сбое, лог.
   С 06.11.2026 (скрипт версии 2) — сам packetlab с закреплённого коммита: `install.sh` с `PL_REF`,
   `PL_NO_DOMAIN=1 PL_YES=1`, затем `packetlab install all` и `packetlab outbounds`; клиент берёт
   Hysteria2 (только salamander, с перескоком портов), REALITY и AnyTLS + REALITY — UDP и TCP рядом
   для сетей с фильтром UDP. Отката нет (packetlab — на чистый Debian, повтор продолжает), 6 шагов.
4. Отчёт для нейронки (файл на рабочий стол) из install.log + состояния сервера.
5. Маршруты «через профиль».
6. «Поделиться»: отдельный пользователь на сервере, ссылка + QR, лимит/срок.

## Открытые вопросы (нужен его выбор)

- SSH: `ssh.exe` из Windows (ничего не тащим, но нужен ключ-файл и разбор вывода) или libssh2
  (полный контроль, ещё одна зависимость в сборке)? Моя рекомендация — `ssh.exe` для начала, он уже
  используется в проекте для проверок.
- Один сервер = один профиль, или сервер может нести несколько профилей (разные протоколы)? Рекомендация:
  один профиль, внутри несколько серверов (по протоколу).
- Где хранить секрет ключа: хранилище клиента (как у подписок?) или файл рядом? Рекомендация: хранилище,
  в tray.json только имя.
- Шаг 1 без установки — достаточно ли для «прикинуть», или хочешь сразу макет формы установки в `client-mockup.html`?
